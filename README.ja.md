# YASAKANI（ヤサカニ）

[English](README.md) · 日本語

<a name="これは何か"></a>

YASAKANI は Windows PC の RTX 1枚で Qwen3.8-27B を動かす推論エンジンです。開発者が動作を確認したのは RTX 5090 だけです。初回のセットアップのあとは、自分の PC だけでチャットやコード編集ができます。いつもの開発ツールからも OpenAI 互換 API でつなげます。0.3.1 からは、Thinking Machines Lab の Inkling-2 Mini も試験的に動かせます（初めは文章だけで、0.3.5 からは静止画も読めます）。0.3.2 からは起動画面で選べます（[詳細](#inkling-2-mini)）。0.3.3 では RTX 50 のカードで速くなり、特に長い入力で差が出ます（RTX 5090 で測定。[詳細](#inkling-2-mini-033)）。

**[Windows 版をダウンロード](https://github.com/yasakani-dev/yasakani/releases/download/v0.3.5/yasakani-quickstart-0.3.5.zip)** · [8エンジンとの速度比較](docs/MEASUREMENTS.ja.md#思考なしreadme-と同じ表反復等を除いた平均toks) · [コード編集の実演動画](https://github.com/yasakani-dev/yasakani/releases/download/v0.3.1/fast_live_uncut.mp4)

## モデルと対応環境

![RTX 5090 1枚・1件ずつ・思考なし。自作の JSONL 編集（60行のうち1行だけ直して全行を返す）で、推奨の品質モデル（本体 12.37 GB）は 2,243 tok/s、最速モデル（本体 10.31 GB）は 2,298 tok/s。v0.1.4・2026年11月15日・2回の平均・入力処理を除く。文脈上限 262,144 トークン。](docs/assets/hero-ja.svg)

JSONL 編集は自作の課題です。60行の JSONL のうち1行だけ直し、全行を返します。答えのほとんどは入力の写しです。tok/s は1秒あたりに生成したトークン数です。思考なしは、答えの前に考えを書き出さない設定です。測った条件は RTX 5090 1枚・1件ずつ・思考なし・v0.1.4（2026年11月15日）・2回の平均です。入力の読み込みは含みません。ほかの GPU では遅くなります。

普段使いには**品質モデル**をおすすめします。予測が元のモデルに近いモデルです。ファイルの小ささと、多くの課題での速さを優先するなら**最速モデル**を選んでください。**最高品質モデル**（15.72 GB）は、3つの中で元のモデルに最も近いモデルです。24 GB 以上のカードが要り、生成は品質モデルの約 0.8〜0.9 倍の速さです（[詳しく](#max-quality-model)）。[品質モデルの配布ページ](https://huggingface.co/yasakani-dev/Qwen3.8-27B-YASAKANI-quality) · [最速モデルの配布ページ](https://huggingface.co/yasakani-dev/Qwen3.8-27B-YASAKANI-speed) · [最高品質モデルの配布ページ](https://huggingface.co/yasakani-dev/Qwen3.8-27B-YASAKANI-max-quality)

0.3.2 から、起動画面の 4 つ目の選択肢に別のモデルの **Inkling-2 Mini** があります（試験的・文章と、0.3.5 からは静止画・依頼は1件ずつ・24 GB 以上のカード。[詳細](#inkling-2-mini)）。

| お使いの GPU | 選べるモデル | Windows での動作確認 |
|---|---|---|
| RTX 5090（32 GB） | 品質・最速・最高品質 | 開発者が実機で検証済み |
| RTX 3090・3090 Ti・4090（24 GB） | 品質・最速・最高品質（最高品質は文脈が短くなる。利用者の報告1件、[#24](https://github.com/yasakani-dev/yasakani/issues/24)） | 対応ビルドあり。開発者は未検証・最適化なし |
| 対象の RTX 40・50 シリーズ（16 GB） | 最速。文脈長は空きメモリに合わせて調整 | 対応ビルドあり。開発者は未検証・最適化なし |

速さの数字は全て RTX 5090 で測った値です。ほかのカードでは遅くなります。速さと動作は保証しません。編集が速いのは、入力から写した多くのトークンを本体が1回の計算で確認するからです（広い写しの計算。1回で最大64トークン）。0.1.7 からは RTX 30・40・50 で、最初の起動時にカードで確認してから使います。16トークンずつの計算とビット単位で同じ予測になり、そのカードで速い幅だけを使います。普通の文章は速くなりません。速くなるのは編集のように入力を写す答えです。

**入力の読み込み（0.2.0 の新機能）：** RTX 5090 では入力を速く読み込みます。答えは変わりません（[0.2.0 で変わったこと](#020-で変わったこと)）。新しい読み方を標準で使うのは、メモリーが 30,000 MiB 以上のカードです。0.3.4 からは 22,000〜30,000 MiB のカードでも、`--max-ctx` で文脈を決めてその横に作業用の領域の分として 1,800 MiB 以上の空きが残る時は使います（RTX 5090 を 24 GB のカードのように設定した私たちの確認では、起動の行は `prompt reading: new (setting auto: 24564 MiB card, 4202 MiB free beside --max-ctx 131072; --prefill old for the 0.1.7 one)` でした）。[#24](https://github.com/yasakani-dev/yasakani/issues/24) の利用者の方の測定にもとづく変更で、24 GB の実機では私たちは動かしていません。ほかのカードは 0.1.7 と全く同じ読み方です。小さいカードでも `--prefill new` で新しい読み方を試せます。これは試験的な設定です。RTX 5090 を 24 GB のカードのように設定した時は新しい読み方を使いました。利用者の方が RTX 3090 Ti（24 GB・Windows 11・0.3.2・品質モデル・文脈は `--max-ctx` で指定）で測り、8,224 と 32,797 トークンの入力を 1.39 倍と 1.40 倍の速さで読みました。自己点検の数字は同じでした。作業用の領域は文脈 131,072 までは作れ、262,144 では作れませんでした（[#24](https://github.com/yasakani-dev/yasakani/issues/24)、報告者の方の数字）。30,000 MiB 未満の実機では、私たちは動かしていません（[小さいカード](docs/FAQ.ja.md#prompt-reading-smaller-cards)）。

**ほかのカードでの報告：** 0.1.7 試験版とその後の版の結果を、利用者の方が [#24](https://github.com/yasakani-dev/yasakani/issues/24) で報告してくださいました。RTX 4090（Windows 10）では確認で3つの幅が全て開き、編集の3課題が広い計算なしの1.85〜1.99倍の速さでした（770.0 → 1,420.9・822.5 → 1,634.9・793.2 → 1,545.6 tok/s）。出力は同じでした。RTX 5060 Ti では64トークンの幅だけが開きました（215.1 → 279.4・226.9 → 300.4・218.8 → 280.6 tok/s、出力は同じ）。RTX 3090（Linux・0.1.7 をソースからビルド）と RTX 3090 Ti（Windows 11・0.3.2）でも確認で3つの幅が全て開き、編集の3課題が1.52〜1.61倍の速さでした。出力は同じでした。どれも報告者の方の数字です。RTX 30・40 向けのコードを私たちが動かしたのは、RTX 5090 の上だけです。[確認の仕組み](docs/FAQ.ja.md#wide-copy-passes-per-gpu)

Linux には寄稿者が検証したソースビルド手順があります。AMD と Mac は今後の対応目標です。[対象 GPU の型番と要件](docs/FAQ.ja.md#どの-gpuどの-os-で動く) · [Linux のビルド手順](BUILDING.md#linux-building-from-source)

**GPU が複数のとき**：1つのプロセスが使う GPU は1枚です。`--device N` で、`yasakani info` と nvidia-smi が N 番とする GPU を選びます。0.1.5 では GPU が2枚の PC で `--device 1` が `graph instantiate failed` で止まることがありました（[#20](https://github.com/yasakani-dev/yasakani/issues/20)）。0.1.6 で直しを入れました。2026年11月18日に、[#20](https://github.com/yasakani-dev/yasakani/issues/20) の報告者が GPU 2枚（RTX A2000 と RTX 5060 Ti）の PC で直ったことを確かめました。私たち自身は GPU 2枚では試していません。

## 使いはじめ

Windows 11（64 ビット）、Python 3.10 以上、NVIDIA ドライバー 580 以上、Visual C++ 2015–2022 ランタイム（x64）、ディスクの空き 20 GB を用意してください。

1. Windows 起動用 ZIP（v0.3.5）を `C:\yasakani` などの英数字のフォルダーに展開します。[配布ファイルと SHA-256](https://github.com/yasakani-dev/yasakani/releases/tag/v0.3.5)
2. **`START.cmd`** を開いてモデルを選びます（1〜3 は Qwen3.8-27B のモデル、4 は試験的な Inkling-2 Mini）。初回はエンジンとモデル一式を取得し、ファイルと GPU の自己点検まで行います。
3. 最後にメニューが出ます。Enter を押すとブラウザーの画面が開き、モデルの読み込みの経過が出ます。読み込みが終わったら質問を入力します。画面のタブは「チャット」「スピード測定」「API 接続」「モデル・状態」の 4 つです。スピード測定はブラウザーの中で測る目安で、標準の測定は `yasakani bench` です。「モデル・状態」には GPU メモリーの使用量が出ます。ダウンロード済みのモデルが 2 つ以上ある時は、ここで切り替えられます。終了ボタンを押すとモデルが止まり、黒い画面も自動で閉じます。
4. 2 回目から（モデルが点検を通ったあと）は、`START.cmd` を開くとこの画面が直接開きます。モデルの質問とメニューは出ません。メニュー（速さを測る・先読みあり・なしを比べる・ターミナルのチャット・サーバーの起動）を出す時は、そのフォルダーのコマンドプロンプトで `START.cmd --menu` と打ちます。

別のアプリから使う時は、画面の「API 接続」のタブに出るアドレスをアプリの接続先にします。通常は `http://127.0.0.1:8765/v1` です。メニューの「サーバーを起動」でも同じ API を使えます。この時は画面を開きません。

ターミナルでは `/effort medium` と入力すると思考が短くなり、`/think off` で思考がオフになります。[手動インストール](python/README.md#install) · [API の使い方](python/README.md#the-server)

**更新。** 0.1.7 から、起動ファイルが自分で更新できます（v0.1.6 以前からは、0.3.5 の起動用 ZIP を一度だけ手で取得してください）。新しい版があるかは、起動のたびに GitHub に問い合わせます（問い合わせる前にそう表示します）。問い合わせるのは、メニューを出す前か、ブラウザーの画面を直接開く前です。新しい版があれば今の版と新しい版を示します。メニューの前では、変える前に必ず聞きます。ブラウザーの画面にも同じ案内と **更新する** のボタンが出ます。画面を直接開く時は黒い画面では聞かず、このボタンを押すまで何も変えません。メニューの「新しい版を確認する」、`START.cmd --action update`、`yasakani update` でも更新できます。0.3.5 から、自動の確認は起動のたびにします（1 時間に 1 回まで）。0.3.4 以前は 1 日に 1 回まででした。前の確認から 1 時間以内の起動では問い合わせません（0.3.4 以前では 1 日以内）。起動したままの起動ファイルも、自分からは確認しません。そのため、新しい版が出た直後は、このボタンが出ないことがあります。すぐに確認する時は、画面の「モデル・状態」の **更新を確認** を押します（0.3.4 から）。どの版でも、起動ファイルのフォルダーで `START.cmd --action update` を実行すれば確認できます。モデルはそのまま使い、エンジンと Python のパッケージは入れ直します。前の版に戻す時は `START.cmd --action rollback` です。自動の確認を止める時は `START.cmd --no-update-check` です。[何を送るか、ファイルをどう確認するか](docs/FAQ.ja.md#更新はどう動く)

## 速度と品質

最速モデルは、7分野すべてで他の8エンジンより速い結果でした。全エンジンを同じ PC の RTX 5090 1枚（定格600 W）で動かし、1件ずつ生成しました。思考なしは反復などを除いた平均、思考ありは課題ごとの最速回で比べています。大きな差が出たのは自作の3課題です。2つは答えの大部分が入力の写しになる編集、1つは規則的な長い JSONL の出力です。この3課題では、思考なしで次に速いエンジンの1.8〜4.6倍でした（コード編集は v0.1.4・11月15日の 2,025 tok/s。MegaCapybara 1.39 Tiny は11月3日の 441 tok/s）。公開されている12問の4分野では1.1〜1.5倍です。12問のうち3問（CUDA のコード、TypeScript のコード、英語の推理小説）は比べていません。最速モデルの答えが反復か指示外のツール呼び出しになったためです。

<a name="020-で変わったこと"></a>

**0.2.0 で変わったこと**（RTX 5090・1件ずつ。公開版の 0.1.7 と比べました）

* **入力の読み込みが速くなりました。** 品質モデルは 8,192 トークンの入力を毎秒 5,153 トークンで読みました（0.1.7 は 4,248、1.21倍）。32,768 トークンでは 4,647 です（0.1.7 は 3,774、1.23倍）。最速モデルは 5,102（4,259）と 4,601（3,774）でした。何も使い回さない最初の読み込みです。思考なしで各版2回の中央値です。文脈長は 69,632 です。思考ありでは、品質モデルがこの2つの長さで1.21倍と1.25倍でした。[詳しく](docs/FAQ.ja.md#prompt-reading-020)
* **読んだことのある長い入力を途中で変えた時は、変えた所の手前の保存した状態から読み直します。** 0.1.7 は最初から読み直していました。32,768 トークンの入力の 25・50・75 % の位置を変えると、品質モデルで1.51倍・2.05倍・4.21倍の速さで読み直しました（最速モデルは1.49倍・2.04倍・4.21倍。条件は同じ）。
* **答えは同じです。** 私たちの確認では、品質モデルと最速モデルで 0.1.7 と同じトークンでした。生成そのものは速くなりません。速度表の15課題（思考なし・全課題の合計・各版3回・置換の再利用は標準のオン）で、0.1.7 と比べて品質モデルは +0.37 %、最速モデルは +0.45 % でした。置換の再利用はこれらの課題を誤差より大きくは速くしません。
* **GPU のメモリーを多く使います。** 最初の長い入力から作業用の領域を持ち続けます。使用量の最大は 0.1.7 より、品質モデルで 1,385〜1,388 MiB、最速モデルで 1,476〜1,479 MiB 多くなりました。GPU にその空きが無い時は `[q35_layer] capacity fallback; no context reduction` を1回表示し、作業用の領域を使わずに読みます（0.2.0 のほかの変更はそのままで、答えは同じです）。標準（`--prefill auto`）で新しい読み方を使うのは 30,000 MiB 以上のカードだけです。それより小さいカードは 0.1.7 と全く同じ読み方です。
* **置換の再利用（新機能、標準でオン）。** 各行のキーや列の名前を変える編集のように、同じ短い置き換えが何度も出る時に効きます。モデルが2か所でその置き換えを書いたあとは、先読みの下書きにその置き換えを入れます。下書きのトークンは全てモデルが確認するので、答えは変わりません。JSONL（80行）の全行でキーの名前を変える課題では、品質モデルで 1,151.4 → 2,039.8 tok/s（1.77倍）でした。SQL（50個のビュー）の全てのビューで列の名前を変える課題では 1,168.5 → 2,101.0 tok/s（1.80倍）です。最速モデルは 1.61倍と 1.60倍でした。条件は文脈長 32,768・温度 1.0・思考なしで、答えの最初の 1,024 トークンを測りました。オフとオンを2回ずつ交互に測った平均です。この2つの課題は `yasakani bench --edit` に入っておらず、入力もこの版には入れていません。置換の再利用は1件ずつ生成する時に働きます。`serve --parallel N` で複数の依頼をまとめた計算では使いません。[詳しく](docs/FAQ.ja.md#edit-copy-020)

どちらも `chat`・`serve`・`bench`・`selfcheck` の設定です。`--prefill auto|new|old`（または `YASAKANI_PREFILL`）と `--edit-copy on|off`（または `YASAKANI_EDIT_COPY`）で変えます。起動時に、どの読み方を使うかとその理由を1行で表示します。[設定の説明](python/README.md#prompt-reading-and-edit-copy) · [測定](docs/MEASUREMENTS.ja.md#measurements-020)

**0.2.0 の新しいモデル：最高品質モデル。** 同じ Qwen3.8-27B を、どの部分も品質モデルより1重みあたり 1 bit 多く変換した物です（15.72 GB）。思考文20本では品質モデルより元のモデルに近く（KL 0.0040 対 0.0126。既定の KV5・RTX 5090）、生成は品質モデルの約 0.8〜0.9 倍の速さです。24 GB 以上のカードが要ります。動作を確認したのは RTX 5090 だけです。起動ファイルでは、モデルの質問の 3 番で選べます。質問が出るのは初回と `START.cmd --menu` の時です。`START.cmd --model max` と打つと、質問なしで選べます。[詳しく](#max-quality-model)

## 複数の依頼を同時に処理する（試験的）

0.1.7 で足した機能です。サーバーは GPU 1枚で複数の依頼を同時に生成できます。依頼ごとに文脈を持ち、モデルの1回の計算で動いている依頼をまとめて進めます。

```bat
yasakani serve --model-dir D:\models\qwen38-quality --parallel 4
```

既定は `--parallel 1` で、今までどおり1件ずつです。この版と GPU のコードが同じ開発中のビルドで確かめました（RTX 5090、両モデル、思考なし）。`--parallel 1` のトークンは各モデル35問で 0.1.5 と同じで、15課題の速さの差は 0.1.5 と比べて1%以内でした。

`--parallel N` でも、各答えのトークンはその会話だけを同じ設定の新しいサーバーに送ったときと同じです。条件は、依頼が自分の `seed` を持つことと、入力の読み方（`timings.snap_mode`）が同じことです。

制限：

* 試験的な機能です。試したのは RTX 5090（32 GB）だけです。
* 編集は遅くなります。コード編集と JSONL 編集では、2〜16件を同時に流すと1件ずつ送るときの0.42〜0.59倍の速さでした。公開の12問は16件同時で1.1〜6.6倍でした（最速モデル、思考なし）。
* 入力を読む間と画像つきの依頼の間は、ほかの依頼がすべて止まります。16,533トークンを読むのに約4.1秒かかります。
* 文脈が短くなります。RTX 5090 で品質モデルを N=4 にすると、1件あたり114,688トークンでした。
* 0.2.0 の新しい入力の読み方：空きを残す `--max-ctx` を指定した時は使いました（RTX 5090 で `--parallel 4 --max-ctx 16384`）。`--parallel N` が文脈長を自分で決める時は、GPU の空きメモリーを使い切ります。その時はエンジンが空きを見つけられず、作業用の領域を使わない読み方になることがあります。これは測っていません。
* `seed` のない依頼は、届いた順番で結果が変わります。

[よくある質問と測定](docs/FAQ.ja.md#複数の依頼を同時に処理する試験的)

## Inkling-2 Mini（試験的。0.3.1 の新機能）

Inkling-2 Mini は、Thinking Machines Lab が 2026 年 11 月 20 日に公開した言語モデルです（[thinkingmachines/Inkling-2-Mini](https://huggingface.co/thinkingmachines/Inkling-2-Mini)）。重みは 264 億個で、専門家を組み合わせる形です。各層は 128 個の専門家から、トークンごとに 8 個を選びます。ライセンスは Apache-2.0 です。モデルカードには利用の規定（[Model Acceptable Use Policy](https://thinkingmachines.ai/model-acceptable-use-policy/)）も書かれています。この規定は重みと、手を加えた版に適用されます。YASAKANI は、エンジンの ZIP に入れた 2 つ目のライブラリでこのモデルを動かします。Qwen3.8-27B のモデルは、これまで通り `yskn.dll` で動きます（#26 と #27 の設定 2 つが増えました。標準では使いません）。

<a name="inkling-2-mini-033"></a>

**速い道（0.3.3 の新機能）。** 0.3.3 では、このモデルをより速く計算する道を足しました。文脈の全体を見る 8 回の層の通過で 8 ビットのキーバリューキャッシュ（公開の規格の MXFP8）を使います。長い文脈を区間に分けて計算する注意と、入力の読み込み用の新しい注意も使います。RTX 50 のカードでは、専門家の入力の計算を 4 ビット（NVFP4）のテンソルコアで行います。標準は `--fast auto` です。0.3.4 からは、RTX 30・40・50 のカード（計算能力 8.6・8.9・12.0）で速い道を使います（0.3.3 では RTX 50 だけでした）。RTX 30・40 のカードでは、RTX 50 だけの 4 ビットの部分を除いて動きます。利用者の方が RTX 3090 Ti で 0.3.3 を測った結果を見て変えました（下の説明、[#29](https://github.com/yasakani-dev/yasakani/issues/29)）。速い道の出力は標準の道に近いですが、同じではありません（下の説明）。そのため RTX 30・40 のカードでは、この更新で標準の出力が変わります。`--fast off`（または `YASAKANI_INK2_FAST=off`）は、どのカードでも速い道を切り、前と同じ計算をします。`--fast on` はほかの GPU でも速い道を使います。速い道を切ると 0.3.2 と同じ計算をします。RTX 5090 では、速い道を切った時のロジットとトークンが 0.3.2 とビット単位で同じでした。同じ GPU の測定の中で比べた 1 回では 1〜2% 遅く、4,096 トークンの後の生成は先読みなしで 160.4 対 163.7 tokens/s、先読みありで 257.8 対 261.0 tokens/s でした。ほかのカードでは測っていません。

0.3.2 と、速い道を使う 0.3.3 の速さです。条件：RTX 5090 1枚・Windows 11・2026 年 11 月 23 日・`--scheme quality` のフォルダー・依頼は1件ずつ・貪欲法。入力は公開のソースファイル 53 本で、繰り返しの無い文です。入力は空の文脈から読みました（2 回の中央値。131,072 トークンは 1 回）。生成は、その長さの入力の直後に `--draft off` で 128 トークン、`--draft auto` で 256 トークンです（3 回の中央値を 2 組。0.3.2 と 0.3.3 は同じ GPU の測定の中で並べて測りました。131,072 トークンは 1 組）。

| | 0.3.2 | 0.3.3・速い道 |
|---|---|---|
| 入力の読み込み・4,096 トークン | 900 tokens/s | 1,826 tokens/s |
| 入力の読み込み・32,768 トークン | 633 tokens/s | 1,755 tokens/s |
| 入力の読み込み・131,072 トークン | 314 tokens/s（418 秒） | 1,377 tokens/s（95 秒） |
| 256／4,096／32,768／131,072 トークンの後の生成・`--draft auto` | 230／257／88／58 tokens/s | 268／351／183／132 tokens/s |
| 256／4,096／32,768／131,072 トークンの後の生成・`--draft off` | 202／162／93／38 tokens/s | 222／209／169／109 tokens/s |
| GPU のメモリー・文脈 33,024／131,072 トークン・先読みあり | 19.9／28.5 GiB | 18.5／20.9 GiB |

標準の文脈は 32,768 トークンです。それより長い入力には `--max-ctx` で長い文脈を指定します（131,072 トークンの数字には、その長さ以上の文脈が要ります）。GPU のメモリーは、読み込み後の GPU 全体の使用量から、起動前の使用量を引いた値です。RTX 50 だけの部分を切った速い道（RTX 30・40 のカードで動く形。RTX 5090 で測定）では、入力の読み込みが 4,096・32,768・131,072 トークンで 1,284・1,236・1,012 tokens/s でした。生成はこの部分を使いません。RTX 30・40 のカードでは、私たちは速い道を動かしていません。利用者の方が RTX 3090 Ti（24 GB・Windows 11）で 0.3.3 を測った報告があります（[#29](https://github.com/yasakani-dev/yasakani/issues/29)。数字は報告者の物です）。`selfcheck` は速い道を入れても切っても合格でした。`bench` の平均は切った時の 101.6 に対して 131.0 tokens/s、読み込みは 4,096 トークンで 256.3 に対して 421.2 tokens/s、32,768 トークンで 171.1 に対して 405.0 tokens/s でした。131,072 トークンの入力は 356 秒で読めました。32K の文脈でエンジンが使う GPU のメモリーは 19.47 GB から 17.87 GB になりました。RTX 40 のカードの報告はまだありません。

速い道は計算の仕方が少し違います（8 ビットのキャッシュ・別のカーネル・足し算の順番）。そのため出力は 0.3.2 と同じではありません。上の文で、4,096 と 32,768 トークンの後の 128 か所を、標準の道（32 ビットのキャッシュ）と比べました。次のトークンの第1候補は 128 か所中 126 か所と 123 か所で一致し、KL の平均は 0.0035 と 0.0059 でした。別の文では、32,768 トークンの後で 128 か所全てが一致しました（KL 0.0043）。そのため貪欲法の出力は、途中から標準の道と分かれます。この測定では、64 トークンの出力が 5 トークン目（4,096 の後）と 31 トークン目（32,768 の後）で初めて違いました。課題の正答率は測っていません。速い道でも、先読みと下の写しで出力は変わりません。コードの編集と JSONL の編集で、使った時と使わない時の出力が同じでした（貪欲法と、種を決めた温度 1.0 の抽選）。

同じ PC で llama.cpp b12600 と比べました。モデルは ggml-org の GGUF `Inkling-2-Mini-IQ4_NL.gguf`（17.63 GB）で、`llama-server -ngl 999 -fa on -np 1` に 8 ビットのキーバリューキャッシュ（`-ctk q8_0 -ctv q8_0`）を付けました。入力は同じトークンの列で、2 回の中央値です（131,072 トークンは 1 回で `-ub 256`。標準の `-ub 512` は 16 ビットのキャッシュでは入らず、8 ビットでも同じ `-ub 256` で測りました）。短い入力は llama.cpp の方が速く読みます。4,096 トークンで 2,119 対 1,826 tokens/s でした。32,768 トークンからは速い道の方が速く、1,755 対 1,467、131,072 トークンで 1,377 対 639 tokens/s でした。生成は先読みなしで比べました（llama.cpp 側に先読みは無い）。256／4,096／32,768／131,072 トークンの後で、222／209／169／109 対 91／90／80／67 tokens/s でした。重みは違います（こちらは 15.05 GB、GGUF は 17.63 GB）。時間の測り方も違い、llama.cpp はサーバー自身の計測、こちらはプロセスの中の経過時間です。131,072 トークンの GPU のメモリーは、llama.cpp が 25.1 GiB、速い道が先読みありで 20.9 GiB でした。

**編集の写し（0.3.3 の新機能・標準では使わない）。** `--copy auto` で使えます。編集のように入力の長い部分を写す答えでは、写した区間を 1 回の計算で確認します。モデル自身が選ぶトークンだけを残すので、出力は変わりません。RTX 5090 で速い道を使い、1 回ずつ測りました。JSONL の編集は、先読みなし・先読みあり・先読みと写しの順に 208・508・791 tokens/s でした。コードの編集は 203・442・716 tokens/s でした。種を決めた温度 1.0 の抽選では 191・414・583 と 187・367・548 tokens/s でした。入力を写さない文では少し遅くなります。短い 12 問では、開発中の版で平均 1.4%、最悪 15% 遅くなりました。

必要な物は次の 3 つです：Windows 11（64 ビット）・24 GB 以上の NVIDIA RTX のカード・YASAKANI 0.3.1 以降の起動ファイルかパッケージ（起動画面で選ぶには 0.3.2 以降。画像には 0.3.5 以降）。画像には Pillow のライブラリーも要ります。0.3.5 の起動ファイルはこれも入れます（パッケージだけの時は `pip install ".[vision]"`）。24 GB 未満のカードにはモデルが入りません。ダウンロードにはディスクの空きが約 20 GB 要ります。変換のプログラムは、同じドライブなら重みのファイルを新しいフォルダーにリンクするので、空きはほとんど減りません（別のドライブではコピーします）。下の手順は Windows の物です。Linux では 2 つの方法があります。どちらもソースから組み立てる物で、公式の配布物ではありません（[BUILDING.md](BUILDING.md#linux-inkling-2)、英語）。1 つは `libyskn.so` の中のエンジンです（`-DYSKN_WITH_INK2=ON`）。@audreyt さんの寄稿です（[#28](https://github.com/yasakani-dev/yasakani/pull/28)・[#30](https://github.com/yasakani-dev/yasakani/pull/30)・[#32](https://github.com/yasakani-dev/yasakani/pull/32)）。ダウンロードしたフォルダーを変換せずに読みます。0.3.5 で速くなり、画像も読めます。プレフィックスキャッシュもあります。もう 1 つは `libyskn_inkling2.so` です（`build_linux.sh`）。@Albrod さんが寄稿した組み立て方です（[#33](https://github.com/yasakani-dev/yasakani/pull/33)）。変換したフォルダーを、速い道・先読み・画像つきで読みます。

**一番早い方法：起動画面（0.3.2 の新機能）。** `START.cmd` のモデルの質問で 4 を選びます（`START.cmd --model inkling2` でも同じです）。起動ファイルが変換済みのコピーを Hugging Face から取得し（0.3.5 の画像用のファイルを含めて約 15.9 GB、変換は不要。0.3.2〜0.3.4 で取得したフォルダーには、そのファイルを足すかを 1 回だけ聞きます。約 0.64 GB です。Enter だけで取得します。`n` なら文章だけのままで、後から `START.cmd --image-file` で足せます）、ほかのモデルと同じく `info`・`verify`・`selfcheck` で点検します。そのあとメニューで Enter を押すと、ブラウザーの画面が開きます。モデルの質問が出るのは、初回と `START.cmd --menu` の時です。24 GB 未満のカードでは選べません。ダウンロードしたあとは、画面のモデルの切り替えにも出ます。自分で用意したフォルダーには、下の方法が使えます。

**手で取得する：変換済みのコピー。** 下で説明する `--scheme quality` で変換した物を、Hugging Face に置いています（[yasakani-dev/Inkling-2-Mini-YASAKANI-quality](https://huggingface.co/yasakani-dev/Inkling-2-Mini-YASAKANI-quality)、15.9 GB、4 ビットの先読み用のモデルと、0.3.5 からは画像用のファイルを含む）。取得したフォルダーを、変換せずにそのまま使えます。起動ファイルのフォルダーでは、先に `yasakani_env.cmd` を実行します。`hf`・`python`・`yasakani` が使えるようになります。

```bat
hf download yasakani-dev/Inkling-2-Mini-YASAKANI-quality --local-dir D:\models\inkling2-mini-quality
yasakani verify --model-dir D:\models\inkling2-mini-quality
START.cmd --model-dir D:\models\inkling2-mini-quality
```

公開のモデルを自分で変換する時は、次の手順です。

1. 公開されているモデルを、Hugging Face のコマンド（`hf`）でダウンロードします。`hf` は Python のパッケージ `huggingface_hub` に入っています。版は私たちが確認した物を指定します。
2. この版のソースにある `tools/convert/inkling2_convert.py` で変換します（公開ページのソースコードの ZIP か、このリポジトリの複製）。標準の設定では重みを変えません。パッケージが使うファイルを隣に作るだけです（各ファイルの SHA-256 を書いた `yasakani.json`・`selfcheck.json`・`NOTICE`）。画像の部分はその重みのファイルに入ったままで、画像入力はそこから読みます（0.3.5 から。Windows ではこの形を動かしていません）。先読み用のモデル（`mtp.safetensors`）は、重みと同じようにフォルダーにリンクかコピーします（下の `--scheme quality` では、代わりに 4 ビットで書き直した物を作ります）。
3. フォルダーを確認してから、チャット・サーバー・ブラウザーの画面のどれかを起動します。

起動ファイルのフォルダーでは、コマンドプロンプトで先に `yasakani_env.cmd` を実行します。起動ファイルの `python` と `yasakani` が使えるようになります。

```bat
cd /d C:\yasakani
yasakani_env.cmd
hf download thinkingmachines/Inkling-2-Mini --revision ed40e7da625f594fc9c4990f5f66be24873c22d7 --local-dir D:\models\Inkling-2-Mini-hf
python C:\src\yasakani-0.3.5\tools\convert\inkling2_convert.py --source D:\models\Inkling-2-Mini-hf --out D:\models\inkling2-mini
yasakani verify --model-dir D:\models\inkling2-mini
yasakani selfcheck --model-dir D:\models\inkling2-mini
yasakani chat --model-dir D:\models\inkling2-mini
yasakani serve --model-dir D:\models\inkling2-mini
START.cmd --model-dir D:\models\inkling2-mini
```

変換のプログラムは、起動ファイルの Python で動かします（`yasakani_env.cmd` で使えるようになる `python`）。変換には numpy・tokenizers・jinja2 が要り、どれもパッケージと一緒にそこに入っています。エンジンのライブラリ `yskn_inkling2.dll` は、コマンドが自分で見つけます。起動ファイルのエンジンのフォルダーで `yskn.dll` の隣にあり、`yasakani_env.cmd` がその `yskn.dll` を指定するからです。`--dll` は、ライブラリを別の場所に置いた時だけ指定します（`yskn_inkling2.dll` か、隣にある `yskn.dll` の場所）。

`selfcheck` は、transformers のライブラリにあるこのモデルの公式の試験（文章）と同じ入力を使います。貪欲法で出した 30 トークンを、その試験の期待値と比べます。`serve` は Qwen のモデルと同じ OpenAI 互換の API で、モデルの ID は `inkling-2-mini` です。`START.cmd --model-dir` は、このフォルダーのモデルでブラウザーの画面を開きます。起動のたびに、先にフォルダーの `info`・`verify`・`selfcheck` をします。私たちの環境では、確認と画面の起動で 35〜40 秒でした（ファイルが Windows のキャッシュにある時）。`START.cmd` のほかの指定は今まで通り使えます。

**速い道を切った時の速さ**（0.3.2 と同じ。RTX 5090 1枚・Windows 11・2026 年 11 月 22 日・公開の重み・1件ずつ）：貪欲法・思考なし・256 トークンの生成は、`yasakani bench --draft off` で 161.2 tokens/s でした。標準の `--draft auto`（下の先読み）では 212.5 tokens/s でした（`bench` の 4 つの入力の平均。温める 1 回の後の 3 回の中央値）。ターミナルのチャット（思考あり・effort low・`--draft auto`）は 155.0 tokens/s でした（日本語の質問 1 つ・375 トークン）。サーバーの逐次の出力は 173 tokens/s で（日本語の短い質問・思考ありで 145 トークン）、最初の出力まで 0.08 秒でした。長い会話では遅くなります（0.3.1 の変更の前のエンジンで測った値。位置 1,024 からは、1 トークンに 7.3〜7.5 ms で、133〜138 tokens/s）。入力の読み込み：パッケージを通して、1,079 トークンの入力で 1,063 tokens/s、4,900 トークンで 961 tokens/s でした（空の文脈から各 3 回の中央値）。前の入力と同じ始まりの入力（チャットの次の番）では、新しい部分だけを読みます。起動から使えるまでは、先読みなしで 6.4 秒、先読みありで 8.5 秒でした（ファイルが Windows のキャッシュにある時）。標準の文脈 32,768 トークンでは、エンジンが GPU のメモリーを 22.7 GB 確保しました（うち KV キャッシュが 2.15 GB）。先読みありでは 23.8 GB です。文脈は `--max-ctx` で変えられます。長くするとキャッシュも増えます。0.3.2 からは `--max-ctx` が無い時、32,768 トークンが GPU の空きメモリーに入ればそのまま使います。入らなければ、入る長さに短くします。どちらにしたかは起動の時に1行で出ます（[コマンドと設定](python/README.md#inkling-2-mini-experimental)、英語）。

**答え。** RTX 5090 で、私たちのエンジンは公式の試験が期待する 30 トークンを出しました。私たちが CPU で書いたこのモデルの実装とも一致しました（隠れ状態の差は 1e-4 以内で、選んだ専門家も同じ）。測ったのは公開のモデルとの一致だけです。課題の正答率は測っていません。

**先読み用のモデル。** 0.3.1 から、モデルに付いている先読み用のモデル（`mtp.safetensors`）を使います。このモデルが次の数トークンを予想し、本体がそれを 1 回の計算でまとめて確認します。本体が選ばないトークンは捨てるので、出力は変わりません。貪欲法では同じトークンになります。サンプリングでも、各トークンを選ぶ確率は同じです。使い方は `--draft` で選びます。標準の `auto` は、生成が速くなる間だけ使います。`on` は常に使います。`off` は読み込みません。環境変数 `YASAKANI_DRAFT` でも同じ設定ができます。`auto` では最大 7 トークンを予想し、本体は予想に自信の無い所の手前までを確認します。`on` で 1 回に予想するトークンの数は `--draft-depth N`（1〜7）で変えられます。起動時の表示に、読み込んだかどうかと使い方が出ます。このファイルが無いフォルダーでも、先読みなしで動きます。

先読みありの速さ（RTX 5090 1枚・Windows 11・2026 年 11 月 22 日・貪欲法・入力ごとに 200 トークン）。パッケージを通して測りました。フォルダーと `--draft` の設定ごとに 1 つのプロセスで、入力を順に流し、3 回の中央値を取りました。入力の数は、日本語の文章とコードが 2 つずつ（どちらも 1 つは思考あり）です。JSON は 1 つ、数学は思考ありの 1 つです。`--scheme quality` のフォルダーの先読み用のモデルは 4 ビットの `mtp_d4.yskn`、公開の重みのフォルダーは `mtp.safetensors` です。1 回の計算で出たトークンは `--draft auto` の値です。

| 文の種類 | 公開の重み・`--draft off` | 公開の重み・`--draft auto` | `--scheme quality`・`--draft off` | `--scheme quality`・`--draft auto` | 1 回の計算で出たトークン（公開 / quality） |
|---|---|---|---|---|---|
| 日本語の文章 | 162.0 tokens/s | 174.5 tokens/s | 205.0 tokens/s | 201.2 tokens/s | 1.32 / 1.11 |
| コード | 162.3 tokens/s | 227.7 tokens/s | 205.3 tokens/s | 225.9 tokens/s | 2.44 / 1.60 |
| JSON | 162.0 tokens/s | 293.2 tokens/s | 204.2 tokens/s | 266.7 tokens/s | 3.64 / 2.30 |
| 数学 | 162.6 tokens/s | 211.8 tokens/s | 204.9 tokens/s | 233.9 tokens/s | 1.89 / 1.77 |

英語の入力 1 つも足した 7 つの合計では、`--draft auto` は公開の重みで 207.2 tokens/s（先読みなしは 162.2）、`--scheme quality` の重みで 223.9 tokens/s（同 204.9）でした。どの回でも、貪欲法の出力は先読みのありとなしで 1 トークンずつ同じでした。予想が当たりにくい文では `auto` が少し遅くなります。`--scheme quality` の重みでは、日本語の文章が 1.5〜2.1% 遅くなりました。`yasakani bench`（その 4 つの入力・思考なし・256 トークン・3 回の中央値）では、公開の重みが `--draft off` で 161.2、`--draft auto` で 212.5 tokens/s でした。`--scheme quality` は 203.8 と 225.9 tokens/s です。

先読みが良く効くのは、次のトークンを予想しやすい文です（コード・JSON・数学）。`yasakani chat` と `yasakani bench` は、1 回の計算で出たトークンの数も表示します。サーバーは `timings` に入れて返します（`tokens_per_pass`・`draft_passes`・`draft_n`・`draft_n_accepted`）。

**小さくした重み（`--scheme quality`）。** 変換のプログラムは、重みを少ないビット数で書き直すこともできます。`--scheme quality` では、密な行列の多くを 4 ビットか 8 ビットにします。層 20〜23 の 8 ビットの専門家は 4 ビットに詰め直します。できるのは 15.05 GB の `.yskn` のファイル 1 つです（公開のファイルは 19.5 GB）。公開のモデルと 43 個の文章（14,024 か所。モデル自身の思考と答え・英語と日本語の文章・コード）で比べると、KL ダイバージェンスは 0.0110 でした。次に最も出やすいトークンは 96.0% の位置で同じでした。先読み用のモデルも 4 ビットで書き直し、重みの隣に `mtp_d4.yskn` として置きます（635.8 MB が 209.7 MB に。`--drafter-scheme published` なら公開のファイルのままです。[FORMAT](docs/FORMAT.md) の 10.6 節、英語）。エンジンはこれらの行列を書いてある形のまま掛けるので、速くなり、GPU のメモリーも減ります。RTX 5090 の 1 回の測定（`yasakani bench`・貪欲法・思考なし・256 トークン・3 回の中央値）では、`--draft off` で 203.8 tokens/s で、公開の重みは 161.2 tokens/s でした。標準の `--draft auto` では 225.9 と 212.5 tokens/s です。標準の文脈 32,768 トークンでのエンジンの確保は 22.7 GB から 18.9 GB に減ります（先読みありでは 23.8 GB から 19.5 GB。4 ビットの先読み用のモデルは 0.56 GB、公開の物は 1.10 GB です）。パッケージを通した入力の読み込みは少し遅く、1,079 トークンで 959 tokens/s（公開の重みは 1,063）、4,900 トークンで 878 tokens/s（同 961）でした（各 3 回の中央値）。起動から使えるまでは、先読みなしで 2.6 秒、先読みありで 3.0 秒でした。変換は CPU で約 4 分です。新しいフォルダーにはディスクが約 15 GB 要ります。画像入力に使う時は `--vision` を付けます。画像の部分を別のファイル（`inkling_2_mini_vision.yskn`、637 MB）に書きます。付けないと、このフォルダーは文章だけです。

```bat
python C:\src\yasakani-0.3.5\tools\convert\inkling2_convert.py --source D:\models\Inkling-2-Mini-hf --out D:\models\inkling2-mini-quality --scheme quality
yasakani verify --model-dir D:\models\inkling2-mini-quality
yasakani selfcheck --model-dir D:\models\inkling2-mini-quality
yasakani chat --model-dir D:\models\inkling2-mini-quality
START.cmd --model-dir D:\models\inkling2-mini-quality
```

`verify` は、各ファイルを SHA-256 で、各テンソルを CRC-32 で比べます。`selfcheck` は短い入力 3 つ（英語・日本語・コード）で、貪欲法の 48 トークンずつを期待値と比べます。期待値は、このモデルの参照の実装が、変換したこの重みで出したトークンです。重みはエンジンが掛けるのと同じ値に戻しました。入力は、48 トークンのどこでも、選ばれたトークンが次の候補よりロジットで 0.11 以上大きい物を選びました（参照の実装でも私たちのエンジンでも）。ほかの GPU で計算の細かい差が出ても結果が変わらないためです。確認したのは RTX 5090 だけです。CPU での変換は、毎回同じファイルになります。`.yskn` のファイルが私たちの変換（版 `ed40e7da625f594fc9c4990f5f66be24873c22d7` から。SHA-256 は `44ef7ea5eade7a1e6cfb4f7ad3f7568a701ce9c621f7e4d00d38b624f4de138d`、15,052,423,172 バイト）と同じなら、変換のプログラムは期待値を `selfcheck.json` に書きます。`START.cmd --model-dir` も、公開の重みと同じようにこのフォルダーを確認します。ファイルが違う時（たとえば別の版から変換した時）は、`selfcheck.json` を空のまま書きます。その時は `selfcheck` に比べる物がありません。`START.cmd --model-dir` で開く時は `--skip-checks` を付けてください（付けないと自己確認で止まります）。

**ツール呼び出し。** 0.3.1 の新機能です。Inkling-2 のフォルダーで `yasakani serve` を使うと、`tools` を受け付けます。モデルの呼び出しは `tool_calls`（finish_reason は `tool_calls`）で返します。ストリームのありとなしのどちらでも使えます。`tool_choice` は `auto`・`none`・`required`・関数名の指定を受け付けます。`auto` では1回の返事に複数の呼び出しも入ります。`required`（ツールが複数でも）と関数名の指定では、モデルは渡したツールの名前でしか呼び出しを書けず、返事は呼び出し1つで終わります。モデルは自分の書式で呼び出しを書き、サーバーがそれを読みます。読めない塊は本文として返します。結果は `tool_call_id` を付けた `tool` のメッセージで送り返してください。ツールありで思考なしの時も、モデルは少し考えます（私たちの測定では 34〜85 トークン。`reasoning_content` に出ます）。この時は思考の量を 0 にして返事を始め、答えか呼び出しの頭をモデル自身に書かせるためです。RTX 5090 1枚と `--scheme quality` のフォルダーで、呼び出し1つ・呼び出しと結果と答え・1回の返事に2つ・ストリーム・`tool_choice` の4種類を流しました。

**制限。** 0.3.1 では試験的な対応です。

* 画像は 0.3.5 から静止画を読めます（[画像入力](python/README.md#inkling-2-mini-image-input)、英語）。動画と動く画像は使えません。画像を付けられるのは user と tool のメッセージだけです。URL の先の画像は取得しません。1,024 画像トークンを超える画像は、先に小さくします（モデルではなく私たちの決まりです）。
* 依頼は 1件ずつです。`--parallel` は使えません。
* ツール呼び出しは `yasakani serve` だけです。ターミナルのチャットでは使えません。ツールを使う会話は、サーバーの文脈（標準は 32,768 トークン）で止まります。入りきらない依頼にはエラー（HTTP 400）を返すので、新しい会話を始めてください。思考ありで長く考えると、呼び出しを書く前に `max_tokens` を使い切ることがあります。`thinking_budget`（依頼の項目か環境変数 `YASAKANI_THINKING_BUDGET`）を付けると、その数のトークンで思考を切ります。
* 多くのアプリは前の返事の思考を送り返しません。そのため次の依頼では前の返事を捨てます。エンジンは 512 位置までなら、会話を読み直さずに捨てられます（`YASAKANI_INK2_ROLLBACK`。0 でエンジンの標準の 64）。その分 GPU のメモリーが増えます。`--scheme quality` のフォルダーと文脈 32,768 では、エンジンの確保が 0.6 GB、GPU 全体では 0.8 GB 増えました（上の確保の値はこの分を含みます）。
* 先読みは、自由な文章より予想しやすい文で良く効きます。効かない所では `--draft auto` が先読みをやめます。それでも時々試すので、少し遅くなります（私たちの測定では `--scheme quality` の重みの日本語の文章で最大 2.1%）。`--draft off` ならこの分は掛かりません。
* このモデルでは `bench --edit` も使えません。
* 私たちが速い道を動かしたのは RTX 5090 1枚だけです。RTX 30 では RTX 3090 Ti の利用者の方の報告があり（上の説明）、RTX 40 のカードの報告はまだありません。出力は標準の道に近いですが、同じではありません（上の説明）。`selfcheck` は、`--fast` を付けない限り標準の道を比べます。
* Windows で確認したのは RTX 5090 1枚と Windows 11 だけです。ほかの GPU では試していません。利用者の方が RTX 3090（24 GB・Windows 11）で 0.3.1 を動かした報告があります（[#29](https://github.com/yasakani-dev/yasakani/issues/29)）。`selfcheck` は合格、`bench` は 105.6 tok/s で、32K の文脈での GPU のメモリーは画面の分を含めて 22.52 GB でした。報告者の方の数字です。Linux では、ソースから組み立てる 2 つの方法があります（[BUILDING.md](BUILDING.md#linux-inkling-2)）。ダウンロードしたフォルダーは `libyskn.so` の中のエンジン（[#28](https://github.com/yasakani-dev/yasakani/pull/28)・[#30](https://github.com/yasakani-dev/yasakani/pull/30)・[#32](https://github.com/yasakani-dev/yasakani/pull/32)）が読みます。変換したフォルダーは `libyskn_inkling2.so`（[#33](https://github.com/yasakani-dev/yasakani/pull/33)）が読みます。私たちはどちらも RTX 5090 1枚の WSL2 だけで動かしました。#28 の寄稿者の方は、RTX 5090 と DGX Spark で動かしています。#33 の寄稿者の方は、画像入力の前の版を RTX 3090 で動かしています。
* 思考なしは私たちの設定です（[よくある質問](docs/FAQ.ja.md#inkling-2-mini)）。

## 開発と支援

YASAKANI はモデルの圧縮形式と GPU の計算を一緒に設計しています。コード編集では、入力からそのまま写せそうな部分を本体が1回の計算でまとめて確かめます。そのため、変えていない行を書き戻す時間が短くなります。[技術解説](docs/TECHNOLOGY.ja.md) · [ファイル形式](docs/FORMAT.ja.md) · [変換ツール](tools/convert/)

<a name="エージェントとして使う"></a>

ソースからのビルド手順と、GPU の動作報告の方法を公開しています。ブラウザーで使うエージェント画面も試せます（任意。GPU のメモリ 24 GB 以上。旧版のサーバーが入っています）。[ビルド](BUILDING.md) · [開発に参加](CONTRIBUTING.md) · [エージェントの導入](harness/HARNESS_README.txt)
