# Release history through 0.3.5

[Back to README](../README.md) · [GitHub releases](https://github.com/yasakani-dev/yasakani/releases)

These release notes used to be at the top of the README. The changes and the contributor references are unchanged. The entries for 0.3.2 to 0.3.5 are short forms of their release pages.

**Version 0.3.5 (November 24, 2026).** Inkling-2 Mini reads still images on Windows: `yasakani chat --image FILE` and `/image PATH` in the chat, OpenAI-style image parts with `data:` URIs in `yasakani serve`, and an **Image** button on the quickstart page when the model reads images. The image tower runs on the GPU inside `yskn_inkling2.dll`. It reads the published tensors, unchanged, from a file of their own, `inkling_2_mini_vision.yskn` (637 MB), which our converted folder on Hugging Face got on November 24, 2026. The quickstart downloads it with the model (about 15.9 GB in all) and offers it once for a folder downloaded by 0.3.2 to 0.3.4 (about 0.64 GB; later `START.cmd --image-file`); `--vision off` does not load it. 0.3.2 to 0.3.4 keep using the new folder as before. Limits: still images only (PNG, JPEG, WebP, GIF, BMP, TIFF; no video or animation), in user and tool messages, no images from URLs, one request at a time, a card with 24 GB or more; an image above 1,024 image tokens is made smaller first, which is our own rule and not the model's. On one RTX 5090 the first 64 tokens of four image prompts equal those of a reference run of the published model, with the fast path and the drafter each on and off, and requests without images gave the same output as 0.3.4, bit for bit, in 21 cases. The design draws on [#32](https://github.com/yasakani-dev/yasakani/pull/32) by @audreyt; we wrote our own version for the Windows engine. `yskn.dll` is that of 0.3.4. From 0.1.7 or newer the quickstart updates itself; from 0.1.6 or older, download the 0.3.5 quickstart ZIP by hand once. We ran it on the RTX 5090 only. Not in this release: [#30](https://github.com/yasakani-dev/yasakani/pull/30) and #32 by @audreyt for the Linux engine. Engine: [release page](https://github.com/yasakani-dev/yasakani/releases/tag/v0.3.5).

**Version 0.3.4 (November 24, 2026).** The fast path of Inkling-2 Mini is now on by default on RTX 30 and 40 cards too: `--fast auto` turns it on for compute capability 8.6, 8.9 and 12.0, on RTX 30 and 40 cards without the RTX 50-only 4-bit part. This follows a user's measurement of 0.3.3 on an RTX 3090 Ti ([#29](https://github.com/yasakani-dev/yasakani/issues/29); the reporter's numbers: `selfcheck` passed with the fast path on and off, `bench` 131.0 against 101.6 tokens/s, prompt reading 405.0 against 171.1 tokens/s at 32,768 tokens). We have run the fast path on the RTX 5090 only, and no RTX 40 card has been reported. Its output is close to, but not the same as, that of the standard path, so the default output on RTX 30 and 40 cards changes; `--fast off` (or `YASAKANI_INK2_FAST=off`) computes as before. On Windows, `--prefill auto` uses the new prompt reading on a card of 22,000 to 30,000 MiB when `--max-ctx` is given and 1,800 MiB stay free beside it ([#24](https://github.com/yasakani-dev/yasakani/issues/24)), and RTX 50 cards keep a wide copy width unless every round is over 0.9 × width / 16 instead of 0.8 ([#31](https://github.com/yasakani-dev/yasakani/issues/31)). Image input for Qwen3.8 (`serve` with the image input options) now opens only PNG, JPEG, WebP, GIF, BMP and TIFF and refuses everything else: before, the image of a request was tried with every format the Pillow library reads, and two of them pass the data on to another program (EPS to Ghostscript when it is installed, WMF and EMF to the renderer of Windows). The Model tab of the quickstart page has **Check for updates**, which asks at once when pressed: the automatic check runs at most once a day, so someone who started the quickstart within the day before a release got no Update button, and a double-click no longer shows the menu (from 0.3.3 or older, `START.cmd --action update` checks at once). `bench --json` for Inkling-2 records the fast and copy settings. `yskn.dll` and `yskn_inkling2.dll` are those of 0.3.3. From 0.1.7 or newer the quickstart updates itself; from 0.1.6 or older, download the 0.3.4 quickstart ZIP by hand once. We ran it on the RTX 5090 only. Not in this release: the faster Linux engine of Inkling-2 Mini ([#30](https://github.com/yasakani-dev/yasakani/pull/30), @audreyt). With the default settings, sampled generation got much slower in our run; we have reported the cause in the pull request and will take it in a following version once that is settled. Engine: [release page](https://github.com/yasakani-dev/yasakani/releases/tag/v0.3.4).

**Version 0.3.3 (November 23, 2026).** This version makes Inkling-2 Mini faster on RTX 50 cards with a fast path: an 8-bit key/value cache (MXFP8, an open format) for the 8 layer visits that attend to the whole context, attention split into parts for long contexts, a new attention for prompt reading, and, on RTX 50 cards, prompt passes of the experts on the 4-bit (NVFP4) tensor cores. It is on by default on RTX 50 cards (`--fast auto`). `--fast on` turns it on on other cards, without the RTX 50-only 4-bit part; we have not run it on an RTX 30 or 40 card. `--fast off` turns it off on any card, and the engine then computes as 0.3.2 did (on the RTX 5090 the same logits and tokens, bit for bit; in one comparison in the same GPU job 1 to 2 % slower). On one RTX 5090 (Windows 11, November 23, 2026, the `--scheme quality` folder, one request at a time, greedy decoding) prompts of 4,096, 32,768 and 131,072 tokens were read at 1,826, 1,755 and 1,377 tokens/s (0.3.2: 900, 633 and 314), and generation with `--draft auto` after 256, 4,096, 32,768 and 131,072 tokens ran at 268, 351, 183 and 132 tokens/s (0.3.2: 230, 257, 88 and 58). The fast path computes in a slightly different way, so its output is close to, but not the same as, that of the standard path: at 128 positions after 4,096 and 32,768 tokens the most likely next token was the same at 126 and 123 of them. Copy decoding for edits is new and off by default (`--copy auto`): the model checks a span copied from the prompt in one pass, and the output does not change. `yskn.dll` and the Qwen3.8 models are those of 0.3.2. The README and the FAQ list the reports from other cards: an RTX 3090 and an RTX 3090 Ti in [#24](https://github.com/yasakani-dev/yasakani/issues/24), an RTX 5060 Ti in [#31](https://github.com/yasakani-dev/yasakani/issues/31), and Inkling-2 Mini on an RTX 3090 in [#29](https://github.com/yasakani-dev/yasakani/issues/29). From 0.1.7 or newer the quickstart updates itself; from 0.1.6 or older, download the 0.3.3 quickstart ZIP by hand once. We ran it on the RTX 5090 only. Engine: [release page](https://github.com/yasakani-dev/yasakani/releases/tag/v0.3.3).

**Version 0.3.2 (November 22, 2026).** An addendum to 0.3.1: Inkling-2 Mini (experimental) can be chosen in the start screen, as choice 4 of `START.cmd` or with `START.cmd --model inkling2`. It downloads our converted copy from [Hugging Face](https://huggingface.co/yasakani-dev/Inkling-2-Mini-YASAKANI-quality) (about 15.3 GB, no conversion) and checks it like the other models. Without `--max-ctx` its context is chosen from the free GPU memory: 32,768 tokens when they fit, else a shorter context, and a line says which. `yskn.dll`, `yskn_inkling2.dll` and the Qwen3.8 models are those of 0.3.1. From 0.1.7 or newer the quickstart updates itself; from 0.1.6 or older, download the 0.3.2 quickstart ZIP by hand once. We ran it on the RTX 5090 only. Engine: [release page](https://github.com/yasakani-dev/yasakani/releases/tag/v0.3.2).

**Version 0.3.1 (November 2026).** This version adds a second model family: [Inkling-2 Mini](https://huggingface.co/thinkingmachines/Inkling-2-Mini) by Thinking Machines Lab (published November 20, 2026; Apache-2.0, with the Model Acceptable Use Policy named on its model card), as an experimental model. It runs on a second engine library in the engine zip. The Qwen3.8-27B models are those of 0.2.0 and 0.2.1; `yskn.dll` adds two options that are off by default: `--suppress-tokens` masks output tokens ([#26](https://github.com/yasakani-dev/yasakani/pull/26), @audreyt), and the experimental `--yarn2` turns on 2x YaRN for contexts up to 524,288 tokens ([#27](https://github.com/yasakani-dev/yasakani/pull/27), @audreyt). Both work with the Qwen3.8 models only ([package README](../python/README.md)). You download the published model from Hugging Face (about 20 GB) and make a model folder with the new converter `tools/convert/inkling2_convert.py`, which does not change the weights by default (with `--scheme quality` it writes them again in fewer bits, 15.05 GB instead of 19.5 GB: KL 0.0110 and the same most likely next token at 96.0 % of 14,024 positions against the published model, with the drafter written again in 4 bits as `mtp_d4.yskn` (209.7 instead of 635.8 MB), faster and smaller in GPU memory because the engine multiplies these matrices as stored (`yasakani bench --draft off` 203.8 against 161.2 tokens/s, 18.9 instead of 22.7 GB allocated), about 4 minutes on the CPU, and checked by `yasakani selfcheck` as well: the conversion gives the same file every time, and the converter writes our expected tokens when the file equals ours); then `yasakani chat`, `serve`, `bench`, `selfcheck`, `verify` and `info` work with that folder, and `START.cmd --model-dir` opens the browser page with it. The commands choose the engine by `"architecture": "inkling2"` in the folder's `yasakani.json`. On one RTX 5090 (Windows 11, published weights, one request at a time) our engine gave the 30 tokens that the official text test of the model's code in the transformers library expects, and it agreed with our own CPU implementation (hidden states within 1e-4, the same experts chosen). Generation with greedy decoding, thinking off and 256 tokens ran at 161.2 tokens/s with `yasakani bench --draft off` and at 212.5 tokens/s with the default `--draft auto` (median of 3 runs; with the `--scheme quality` folder 203.8 and 225.9 tokens/s); prompts are read at about 1,000 tokens/s (961 tokens/s for 4,900 tokens through the package); with the default context of 32,768 tokens the engine allocated 22.7 GB of GPU memory, so it needs a card with 24 GB or more. The package also uses the drafter that comes with the model (`mtp.safetensors`; `--draft auto|on|off`, default `auto`): it guesses the next few tokens and the model checks them in one pass, so the output does not change (greedy gave the same tokens with and without it in all our runs). With `--draft auto` it guesses up to 7 tokens and the model checks them up to the first one the drafter is unsure of. The speed depends on the text (published weights, 200 tokens: code 227.7, JSON 293.2, Japanese prose 174.5 against about 162 tokens/s without it); `auto` stops drafting where it does not pay, at a small cost there. The table is in the [README](../README.md#inkling-2-mini). `yasakani serve` also takes tool calls for this model, with and without streaming (draws on [#28](https://github.com/yasakani-dev/yasakani/pull/28) by @audreyt). On Linux, Inkling-2 Mini can run on another engine inside `libyskn.so`, which you build from source with `-DYSKN_WITH_INK2=ON` and which reads the downloaded folder without conversion; the released Windows `yskn.dll` does not contain it ([#28](https://github.com/yasakani-dev/yasakani/pull/28), @audreyt; its author ran it on an RTX 5090 and a DGX Spark, we on one RTX 5090 under WSL2; [BUILDING.md](../BUILDING.md#linux-inkling-2)). Limits: text only, one request at a time, tool calls in `yasakani serve` only, and run on the RTX 5090 only. From 0.1.7, 0.2.0 or 0.2.1 the quickstart updates itself; from 0.1.6 or older, download the 0.3.1 quickstart ZIP by hand once. Engine: [release page](https://github.com/yasakani-dev/yasakani/releases/tag/v0.3.1).

**Version 0.2.1 (November 21, 2026).** This version changes the Windows quickstart only; the engine library and the models are those of 0.2.0. From the second run on, `START.cmd` opens the browser page directly, without the model question and the menu (`START.cmd --menu` shows the menu; there the browser chat is item 1 and Enter picks it). The page opens before the model is loaded and shows the loading with the seconds; when the model is ready, you can chat without reloading the page. The page has four tabs: chat (with a choice of how much the model thinks and copy buttons on code), a speed test (a rough figure measured in the browser), the API address with samples for other programs, and model / status (GPU memory, a switch between the models you have downloaded, and quit). The quit button stops the server, frees the GPU memory and closes the launcher's window. On our RTX 5090 PC, with the models downloaded and checked before and the browser already running, the page was open 0.5 s after the start (one start) and the quality model was ready after 7 and 10 s (two starts). This version also fixes an error during an update that was started with the page's **Update** button: the new start files tried to replace the engine while the server of the version before was still ending; they now wait for it. From 0.1.7 or 0.2.0 the quickstart updates itself; from 0.1.6 or older, download the 0.2.1 quickstart ZIP by hand once. We ran it on the RTX 5090 only. Engine: [release page](https://github.com/yasakani-dev/yasakani/releases/tag/v0.2.1).

**Version 0.2.0 (November 20, 2026).** This version reads prompts faster on the RTX 5090, adds the edit copy and adds a third model, the max-quality model. Prompt reading: the first read of a prompt is computed layer by layer in larger pieces, and the output layer only where it is needed. Quality model, RTX 5090, the first read of a prompt, thinking off, one request at a time, median of 2 runs: 5,153 input tokens/s at 8,192 tokens (0.1.7: 4,248) and 4,647 at 32,768 tokens (0.1.7: 3,774), with the same answers as 0.1.7. A known long prompt that changes in the middle is read again from the last saved state before the change: a 32,768-token prompt changed at 25 %, 50 % and 75 % was read again 1.51, 2.05 and 4.21 times as fast (quality model, RTX 5090). The new reading takes more GPU memory on the RTX 5090 (at the peak 1,385 to 1,388 MiB more with the quality model, 1,476 to 1,479 MiB with the fastest model), and by default (`--prefill auto`) it is used only on cards with 30,000 MiB or more. Smaller cards read prompts exactly as 0.1.7 did. `--prefill new` on a smaller card is experimental and was never run on a real card of that size (on the RTX 5090 set up as a 24 GB card it used the new reading; set up as a 16 GB card it found no room at the context the package chose); `--prefill old` reads as 0.1.7 did on any card. The edit copy (on by default; `--edit-copy off` turns it off): when an edit replaces the same text again and again, the copy passes reuse the replacements the model has already confirmed, and the output does not change (a JSONL key renamed in every line: 1.77 times as fast, quality model, RTX 5090, thinking off, one request at a time). It acts when one request is generated at a time; the shared passes of several requests at once do not use it. Generation speed is otherwise unchanged (the 15 tasks of the speed tables with the edit copy on: +0.37 % quality model, +0.45 % fastest model, thinking off, one request at a time). The check of the wide copy passes on the card now also covers passes of 64 tokens after position 4,096, so it runs once more after the update. The max-quality model is the same Qwen3.8-27B with one bit per weight more than the quality model in each part (15.72 GB): on 20 thinking texts, KL 0.0040 and the same most likely next token at 97.40 % of positions (quality model 0.0126 and 95.35 %; default KV5, RTX 5090), and generation at about 0.8 to 0.9 times the speed of the quality model. It needs a card with 24 GB or more and YASAKANI 0.2.0 or newer, and the quickstart offers it as choice 3 ([measurements](MEASUREMENTS.md#max-quality-model)). From 0.1.7 the quickstart updates itself; from 0.1.6 or older, download the 0.2.0 quickstart ZIP by hand once. We measured on the RTX 5090 only ([measurements](MEASUREMENTS.md#measurements-020)). Engine: [release page](https://github.com/yasakani-dev/yasakani/releases/tag/v0.2.0).

**Version 0.1.7 (November 19, 2026).** This version adds updates, wide copy passes on RTX 30 / 40 cards and, as an experiment, several requests at once. Updates: the quickstart asks GitHub for a newer release at most once a day, shows the old and the new version and asks before it changes anything. It keeps the old start files, and `START.cmd --action rollback` goes back to them. The browser chat shows the same offer with an **Update** button, and `yasakani update` starts the same update (see [How does the update work?](FAQ.md#how-does-the-update-work)). From 0.1.6 or older, download the 0.1.7 quickstart ZIP by hand once. Several requests at once: `yasakani serve --parallel N` generates up to N requests at the same time on one GPU. It is experimental and off by default: `--parallel 1` serves one request at a time, as before. It was tested on the RTX 5090 only, and edits are slower with it (see [Several requests at once](../README.md#several-requests-at-once)). Measurements of development builds: [Measurements](MEASUREMENTS.md#several-requests-at-once-experimental). Wide copy passes: the passes that check up to 64 copied tokens at once (since 0.1.4, on RTX 50 cards only) are now used on RTX 30 / 40 cards too, after a check on the card at the first start (first tried in the 0.1.7 test build, [v0.1.7-test1](https://github.com/yasakani-dev/yasakani/releases/tag/v0.1.7-test1), a pre-release). A width is used only if it gives the same predictions as 16-token passes, bit for bit, and is faster on that card; on RTX 50 cards the same check leaves out a width that is slower there. The check runs again after an update (on the RTX 5090 it took 21.8 to 22.9 seconds with the 0.1.7 test build). Only answers that copy the input, such as edits, get faster. `--wide off` turns them off, and `yasakani report` prints a report to paste on GitHub (see [the FAQ](FAQ.md#wide-copy-passes-per-gpu)). Users of the 0.1.7 test build reported an RTX 4090 and an RTX 5060 Ti in [#24](https://github.com/yasakani-dev/yasakani/issues/24); no RTX 30 card has been reported yet, and we ran the code for RTX 30 / 40 only on the RTX 5090. A fix: the engine now keeps at most 32 CUDA graphs for the passes that read a prompt and drops the one used longest ago. Before, a server kept one graph for every prompt length it had read, so its GPU memory could grow over hours. The README lists a second community conversion, Arete-27B-pi by @audreyt ([#23](https://github.com/yasakani-dev/yasakani/pull/23)). Loading a model no longer stalls on the DGX Spark (GB10, Linux ARM64): on that device the weights go to the GPU through a small staging buffer, and other GPUs copy them as before ([#25](https://github.com/yasakani-dev/yasakani/pull/25), checked by its author on a DGX Spark). Engine: [release page](https://github.com/yasakani-dev/yasakani/releases/tag/v0.1.7).

**Version 0.1.6 (November 18, 2026).** This version adds two things. First, `yasakani bench --edit` runs the three edit tasks of the speed tables on your PC with one command. It prints the speed, the tokens per pass and whether each answer is the expected one (see [Speed](../README.md#speed)). Second, a fix for PCs with several GPUs ([#20](https://github.com/yasakani-dev/yasakani/issues/20)). With 0.1.5, `--device 1` on a PC with two GPUs could stop with `graph instantiate failed` while the other GPU was visible. The engine now selects its GPU on every call, not only on the thread that opened it. `chat`, `serve`, `bench` and `selfcheck` let the engine see only the GPU of `--device` (unless nvidia-smi gives no UUID for it; see [What you need](../README.md#what-you-need)). With one GPU the generated text (greedy) and the speed are those of 0.1.5 (checked on the RTX 5090); it has not yet been tried on a PC with two GPUs. (Added later: on November 18, 2026 the reporter of [#20](https://github.com/yasakani-dev/yasakani/issues/20) confirmed the fix on a PC with two GPUs.)

**Version 0.1.5 (November 16, 2026).** This version is a set of fixes, most of them contributed. Tool calls with `<function=...>` inside a JSON argument are read correctly, the same image twice in one request is encoded once, and `--dll` or `YASAKANI_DLL` naming a file that is not there stops with an error instead of loading another library ([#12](https://github.com/yasakani-dev/yasakani/pull/12)). A tool-call argument declared as a boolean also takes Python's `True` / `False`. An argument that may be null also takes `None` ([#21](https://github.com/yasakani-dev/yasakani/pull/21)). The engine reads the header length of a model file as 64 bits ([#14](https://github.com/yasakani-dev/yasakani/pull/14)), attends to the whole of a short context also when `YSKN_Q35_ATX_SPLITS` is set below 31 (the default, 42, was not affected; [#15](https://github.com/yasakani-dev/yasakani/pull/15)), and keeps the look-ahead state of two engines in one process apart ([#13](https://github.com/yasakani-dev/yasakani/pull/13)). Its GPU code is that of 0.1.4, so the speed tables stand. `--max-ctx` leaves out the output head of the draft model when it does not fit beside the given length ([#17](https://github.com/yasakani-dev/yasakani/pull/17)). On a PC with several GPUs, `--device N` is now GPU N of `yasakani info` and nvidia-smi ([#20](https://github.com/yasakani-dev/yasakani/issues/20)). The FAQ says that a monitor on the same GPU can slow generation ([#18](https://github.com/yasakani-dev/yasakani/issues/18)). 0.1.4 made edits faster and reads long prompts again less often. Where the answer copies the input, one pass checks up to 64 copied tokens instead of 16. With thinking off, code and JSONL edits are 1.67 to 2.04 times as fast as with 0.1.2, the other tasks run at 0.96 to 1.01 times (as fast as 0.1.3 measured in the same sitting: 0.99 to 1.00 times), and the answers are the same (see [Speed](../README.md#speed)). The quickstart now checks the NVIDIA driver before it downloads anything, and `yasakani selfcheck` also checks GPUs other than the RTX 5090 (see [What you need](../README.md#what-you-need)). The same long document followed by a different question is no longer read again from the start (when the document comes before the question and no other request comes in between): after a 229,376-token document the first token comes after 0.37 s instead of 116 s (see [Long contexts](../README.md#long-contexts)). The server now also accepts `tool_choice` `required` and a named function (not enforced) and reports llama.cpp-style `timings`, and image input also works on Linux with llama.cpp built from source (all three contributed in [#8](https://github.com/yasakani-dev/yasakani/pull/8); image input on Linux not tried by us); [BUILDING.md](../BUILDING.md#linux-building-from-source) has a Linux section ([#10](https://github.com/yasakani-dev/yasakani/pull/10), [#8](https://github.com/yasakani-dev/yasakani/pull/8)). Since 0.1.3 the engine is also built to run on other NVIDIA RTX 30, 40 and 50 series cards with 16 GB or more; we have not run it on them, and it is not optimized for them (see [What you need](../README.md#what-you-need)). 0.1.3 also fixed the cause of a rare change of the text part-way through a run (see [Quality](../README.md#quality)). Since 0.1.2 the server can take images, optionally (contributed in [#4](https://github.com/yasakani-dev/yasakani/pull/4)). Since 0.1.1 it accepts requests with `tools` (tool / function calling), so coding agents and other tool-using apps can connect to it. Engine: [release page](https://github.com/yasakani-dev/yasakani/releases/tag/v0.1.5). Models on Hugging Face: [quality model](https://huggingface.co/yasakani-dev/Qwen3.8-27B-YASAKANI-quality) and [fastest model](https://huggingface.co/yasakani-dev/Qwen3.8-27B-YASAKANI-speed).
